# Техническое задание на сервис анализа поисковых запросов и SEO-правок

## Цель

Сервис помогает владельцу сайта ответить на два вопроса. Что стоит улучшить на страницах, которые уже показываются в поиске? Что изменилось после публикации правки?

Пользователь загружает файл с парами «поисковый запрос и URL». За один запуск сервис анализирует до 20 уникальных страниц, группирует запросы по задачам посетителей и готовит список проверяемых рекомендаций. Пользователь может записать опубликованную правку и позже загрузить второй файл для сравнения. Сервис работает с выгрузками. Доступ к аккаунтам Google и Яндекса ему не нужен.

Рабочий процесс основан на уроках [о сборе запросов](src/content/courses/seo/lessons/query-research.md) и [об оценке изменений](src/content/courses/seo/lessons/measure-seo-changes.md).

## Работа без ИИ

Импорт, группировка запросов, анализ HTML, рекомендации и сравнение периодов выполняются детерминированными алгоритмами. Сервис не использует внешние ИИ API, локальные языковые модели или эмбеддинги. Для анализа запросов используются нормализация текста, словари, правила и поиск совпадений. Сетевой доступ требуется для получения публичных страниц.

При повторном запуске на той же выгрузке, тех же снимках HTML и той же версии правил результаты анализа совпадают. Сохраняем версию правил вместе с отчётом, чтобы его можно было воспроизвести после обновления словарей.

## Импорт данных

Для первого анализа пользователь загружает один файл. Для измерения результата он загружает ещё один файл в тот же проект. Оба отчёта связываются с записью о правке.

| Формат | Обязательные поля | Дополнительные поля |
| --- | --- | --- |
| Универсальный CSV | `url`, `query` | `date`, `clicks`, `impressions`, `position`, `device`, `region` |
| CSV расширенной аналитики Яндекс Вебмастера по URL | URL и запрос | Дата, хост, регион, клики, показы, позиция |

При импорте сервис показывает распознанные колонки, период и количество страниц. Если источник, период или фильтры отсутствуют в файле, пользователь может указать их при импорте. Для качественного анализа эти поля необязательны. Для сопоставления периодов они нужны в той мере, в какой определяют сравниваемую выборку.

Стандартная выгрузка Search Console по всему сайту содержит агрегаты по запросам и страницам. Для импорта Google используем универсальный CSV, собранный из данных с совместными измерениями `page` и `query`. Если файл содержит только запросы, допустим ввод одного явно выбранного URL для выгрузки, которую пользователь заранее отфильтровал по этой странице. Связи между отдельными таблицами страниц и запросов сервис не восстанавливает. [Экспорт Search Console](https://support.google.com/webmasters/answer/12919797) · [Search Analytics API](https://developers.google.com/webmaster-tools/v1/searchanalytics/query) · [Экспорт по URL в Яндекс Вебмастере](https://yandex.ru/support/webmaster/ru/service/queries-export)

Требования к обработке файла:

- Один сайт и один поисковик на импорт. Сопоставление Google и Яндекса показывается отдельными отчётами.
- Лимит составляет 20 уникальных URL после нормализации. При превышении пользователь выбирает страницы для анализа.
- Нормализация приводит схему и хост к стандартному регистру и удаляет якорь. Путь, завершающий слеш и параметры сохраняются. Редиректы и объявленный canonical записываются отдельно.
- Строки с пустым запросом, некорректным URL или отрицательными метриками выводятся с номером строки и причиной. Перед запуском пользователь видит, какие строки войдут в отчёт. Точные дубли помечаются, чтобы случайно не удвоить метрики.
- Отсутствующие метрики сохраняются как неизвестные. Ограничения по размеру файла и количеству строк на запуск должны быть настраиваемыми.

## Анализ страниц и запросов

1. Сервис загружает публичный HTML каждого уникального URL. Сохраняет время проверки, итоговый адрес, HTTP-статус, `title`, H1, подзаголовки, метаописание, `canonical`, `noindex` и основной текст. Ошибка одной страницы сохраняется в отчёте, остальные продолжают обрабатываться.
2. Запросы группируются внутри страницы по распознанной теме и признаку задачи. Сервис нормализует регистр и пробелы, выделяет слова и применяет словари русских и английских формулировок. Например, «обязателен ли sitemap» и «зачем нужен sitemap» можно связать через правило о назначении карты. «Ошибка обработки sitemap» остаётся отдельной группой диагностики. Неоднозначные запросы остаются без группы до проверки. Пользователь может переименовать, разделить или объединить группы.
3. Для каждой группы сервис ищет признаки ответа в `title`, H1, подзаголовках и основном тексте. Результаты автоматической проверки: «найдены признаки ответа», «найдены частичные признаки», «признаки не найдены» и «недостаточно данных». Отчёт показывает совпавшие слова или фразы, раздел страницы и фрагмент исходного текста. Если текст получить не удалось, в отчёте указывается причина, а покрытие не оценивается. Полноту ответа подтверждает пользователь.
4. Сервис предлагает до трёх правок на страницу по шаблонам правил. Например, если запрос содержит «как сгенерировать sitemap», а поиск по основному тексту не находит шагов сборки, сервис предлагает проверить, нужен ли в статье пример генерации с командой проверки. Рекомендация указывает сработавшее правило и наблюдение, по которому её можно проверить.
5. Приоритет определяется по опубликованным правилам. Сначала идут подтверждённые технические проблемы, затем группы с признаками пробела в ответе. Внутри одной категории вверх поднимаются группы с большим числом показов. Если показов нет в файле, используем стабильный порядок по URL и названию группы. Низкий CTR служит поводом для проверки сниппета и позиции.

В первой версии анализ опирается на запросы из файла и полученный HTML. Намерение пользователя оценивается как гипотеза. Техническая проверка описывает полученный ответ сервера. Статус страницы в индексе и живая выдача требуют отдельных источников данных.

### Быстрые фильтры по запросам

В отчёте пользователь может отобрать запросы по формулировке, чтобы быстрее найти темы для проверки. Сервис применяет правила к запросам из загруженного файла. Настраивать регулярные выражения в поисковой панели не нужно.

| Фильтр | Что ищем в выгрузке |
| --- | --- |
| Длина | Запросы от 4, 8 или 10 слов. Длина помогает отобрать подробные формулировки для просмотра. |
| Вопросы и инструкции | «Что такое», «зачем», «можно ли», «как настроить», «пошагово». |
| Диагностика | «Ошибка», «не работает», «почему не индексируется». |
| Сравнение и выбор | «Отличие», «альтернатива», «что лучше», «отзывы». |
| Цена и покупка | «Сколько стоит», «цена», «купить», «скидка». |
| Регион и наличие | «Рядом», «в наличии», «доставка». Такие фразы дают повод проверить локальный контекст и условия услуги. |
| Дополнительные темы | Признаки актуальности, поддержки, характеристик или поиска инструмента, например «актуальная версия», «гарантия», «размеры», «генератор». |

Для первой версии подготовить наборы выражений для русского и английского. Сопоставление учитывает регистр и границы слов для кириллицы. Для русских формулировок покрываем распространённые словоформы и сочетания с английскими терминами. Один запрос может совпасть с несколькими фильтрами. Рядом с меткой показываем совпавший фрагмент. Показы и клики в общей выборке считаются по исходным строкам, даже если у одной строки несколько меток.

Совпадение по фразе помогает отобрать запрос для просмотра. При анализе страницы ищем признаки ответа на предполагаемую задачу читателя. Например, «генератор robots.txt не работает» подходит под фильтры диагностики и инструментов, но рекомендация зависит от того, описывает ли страница настройку генератора или помогает исправить ошибку. Фразы вроде «покажи» или «объясни» можно найти как разговорные формулировки. По ним нельзя установить, что запрос пришёл из сервиса ИИ.

В отчёте пользователь может включить несколько фильтров, увидеть число совпадений и открыть исходные запросы. Фильтры применяются и к CSV без метрик. При наличии показов результаты можно отсортировать по их числу. Выбор фильтра сам по себе не меняет группу запросов, сохранённую в журнале правок.

## Журнал правок

Пользователь может сохранить рекомендацию как правку, изменить её или добавить свою. Запись хранит:

- URL и выбранные запросы или сохранённую группу;
- что изменилось, дату публикации и ссылку на исходный отчёт;
- гипотезу и основной показатель наблюдения;
- дату повторной проверки и известные сопутствующие изменения;
- статус «запланировано», «опубликовано» или «проверено».

Например, для урока о sitemap пользователь меняет заголовок и выбирает CTR по запросам об обязательности карты. В журнале остаются исходные показы, клики и позиция. Состав проверяемой группы фиксируется на момент начала измерения.

## Отчёт до и после

Пользователь выбирает запись о правке и загружает повторную выгрузку. Сервис сопоставляет строки по источнику, URL, запросу и доступным фильтрам. Анализ использует те же запросы, которые были сохранены в журнале. Новые запросы показываются отдельно.

- Сравниваем полные периоды равной длины с одинаковым набором дней недели. Если пользователь знает, когда обновлённая страница начала появляться в выдаче, период «после» можно начать с этой даты. Даты, поисковик, устройство и регион должны быть видны рядом с числами.
- Суммируем показы и клики. CTR рассчитываем как отношение суммы кликов к сумме показов. При нуле показов CTR остаётся неопределённым. Изменение CTR показываем в процентных пунктах.
- Среднюю позицию объединяем с весом по показам только там, где определение поля источника и полнота данных позволяют это делать. В остальных случаях показываем позиции на исходном разрезе или отмечаем, что сводное значение недоступно.
- Если запрос отсутствует во второй выгрузке, помечаем его как «нет строки в выгрузке». При неполных данных сервис объясняет, какие метрики удалось сопоставить. Для недостаточного объёма данных показывает числа и просит осторожно интерпретировать изменение.
- Вывод описывает наблюдение и возможные объяснения. Например, «CTR вырос с 4% до 6%, одновременно средняя позиция улучшилась с 9,1 до 4,8». Привязка к правке остаётся гипотезой.

## Интерфейс и результаты

Пользователь проходит четыре экрана: импорт и проверка колонок, список приоритетов и отчёты по страницам, журнал правок, сравнение периодов. На странице отчёта доступны фильтры по URL, теме и результату проверки. Список рекомендаций и сравнение выгружаются в CSV. По каждому запуску показываются результаты, ошибки страниц и настройки импорта.

Первую версию предлагается реализовать как отдельное веб-приложение. Сервер получает публичный HTML, а фоновая задача выполняет импорт и анализ. Хранилище связывает пользователя, проект, импорты, снимки страниц, рекомендации и журнал. Сервер применяет версионируемые словари и правила, извлекает фрагменты непосредственно из сохранённого HTML и рассчитывает метрики по исходным строкам.

Для загрузки страниц используем HTTP(S) с проверкой публичного адреса при исходном запросе и на каждом перенаправлении, ограничениями на объём, время и параллельность. Файлы и отчёты доступны только владельцу проекта. Пользователь может удалить проект вместе с данными. Загруженный HTML используется как вход анализа и отображается в отчёте безопасным текстом.

Автоматическое изменение сайта, обход всего домена, рендеринг JavaScript, анализ живой выдачи и OAuth-подключения можно рассмотреть после проверки первого сценария.

## Критерии приёмки

1. Один CSV с несколькими запросами на каждый из 20 URL создаёт отчёты по всем 20 страницам. При 21 URL пользователь может выбрать 20. Ошибка загрузки одного URL не прерывает остальные проверки.
2. CSV Яндекс Вебмастера и универсальный CSV импортируются через один экран. Файл Google без соответствия между запросами и страницами получает понятное объяснение, какие данные добавить.
3. Для каждой рекомендации видны исходные запросы, URL и фрагмент страницы либо причина, по которой текст недоступен. Пользователь может поправить группировку и сохранить рекомендацию в журнал.
4. Повторная выгрузка даёт сравнение по сохранённой группе и исходным фильтрам. Например, 40 кликов при 1 000 показах и 60 при 2 000 дают 4% и 3% CTR, разницу в −1 процентный пункт и 20 дополнительных кликов.
5. Пропущенная строка, ноль показов и несопоставимые фильтры отражаются в отчёте с объяснением. Ни один из этих случаев не превращается автоматически в вывод о результате правки.

6. Фильтр диагностики находит «генератор robots.txt не работает», а фильтр инструментов находит тот же запрос по слову «генератор». При включении обоих фильтров запрос виден одной строкой с двумя метками, его показы и клики учитываются один раз. Запрос «что такое canonical» попадает в вопросы, но не в диагностику.
7. При отключённых внешних ИИ-сервисах полный сценарий от импорта до отчёта и сравнения периодов работает. Два запуска на одинаковых входных данных и версии правил дают одинаковые группы, оценки и рекомендации. Если по запросу или странице недостаточно признаков, отчёт оставляет его на ручную проверку.
