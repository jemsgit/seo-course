# Нормализация и createEntityAdapter

<div className="learning-note"><strong>После урока ты сможешь</strong><p>Читать структуру ids/entities и обновлять сущности через adapter.</p></div>

Перед началом: пройди [предыдущий урок](/redux/lessons/memoization/).

## Что такое нормализация

Нормализация — способ организовать данные так, чтобы каждую сущность хранить в одном месте, а из других записей ссылаться на неё по id. Сущность — отдельная запись с идентификатором: задача, пользователь или комментарий.

Например, у двух задач один исполнитель. Если хранить полный объект пользователя внутри каждой задачи, изменение имени придётся повторять в нескольких местах. Вместо этого можно хранить пользователя в `users.entities`, а в задачах — только `assigneeId`. Тогда имя меняется в одной записи пользователя.

Это идея организации данных, а не отдельная возможность Redux. `createEntityAdapter` помогает поддерживать выбранную структуру, но не превращает произвольный вложенный ответ сервера в набор связанных таблиц автоматически.

## Сначала обычный массив

В предыдущих примерах задачи могли храниться так:

```ts
const tasks = [
  { id: '1', title: 'Понять store', done: true },
  { id: '2', title: 'Написать slice', done: false },
];
const task = tasks.find(task => task.id === '2');
```

Массив сразу задаёт порядок элементов. Но для поиска конкретной записи по id приходится проходить по нему. Для небольшой коллекции это вполне нормальный вариант.

## Зачем нужны и entities, и ids

`createEntityAdapter` использует две части состояния с разными задачами:

```js
const tasks = {
  ids: ['2', '1'],
  entities: {
    '1': { id: '1', title: 'Понять store', done: true },
    '2': { id: '2', title: 'Написать slice', done: false },
  },
};
```

- **`entities` отвечает на вопрос «где данные записи с таким id?»** Можно обратиться к `tasks.entities['2']` без поиска по массиву.
- **`ids` отвечает на вопрос «какие записи входят в коллекцию и в каком порядке их обходить?»** В примере задача `'2'` идёт раньше задачи `'1'`.

В `ids` лежат только идентификаторы, а не вторые копии задач. Заголовок и `done` по-прежнему хранятся в одном месте — в `entities`.

Список для отображения можно собрать в нужном порядке:

```js
const orderedTasks = tasks.ids.map(id => tasks.entities[id]);
// Сначала «Написать slice», затем «Понять store».
```

Это иллюстрация для JavaScript. В TypeScript ключи и типы коллекции нужно описать; дальше используем готовый типизированный селектор `selectAll` от adapter, который выполняет такую сборку.

### Почему не обойтись Object.values(entities)?

Получить значения объекта можно. Но порядок перечисления ключей JavaScript не обязан совпадать с нужным порядком интерфейса. Например, ключи `'1'` и `'2'` перечисляются как целочисленные: `Object.values` в этом примере даст сначала задачу `'1'`, хотя в `ids` первой стоит `'2'`.

Отдельный массив позволяет явно задать порядок коллекции, не перемещая и не копируя сами записи. Он также удобен, когда компонент списка выбирает только ids, а каждая строка читает свою запись по id.

Нормализация в целом не требует именно названий `ids` и `entities`. Можно спроектировать свою структуру. Но **для состояния createEntityAdapter обе части — установленный формат**, и методы adapter поддерживают их согласованность: при добавлении записи обновляются обе части, при удалении id убирается и из списка, и из словаря.

## Когда такая форма полезна

Нормализация особенно помогает, если записи часто обновляются по id, используются в нескольких местах или связаны друг с другом. Она уменьшает дублирование данных и упрощает точечные изменения.

Это не обязательный переход для любого массива. Небольшой простой список может оставаться массивом. В этой главе мы намеренно меняем представление, чтобы изучить другой способ хранения коллекции. Само преобразование не меняет смысл задач и не гарантирует ускорения всего приложения: построение полного списка всё равно требует обхода элементов.

## Откуда берутся addOne и getInitialState

**Эти функции уже написаны авторами Redux Toolkit. Самостоятельно реализовывать их не нужно.** Вызов `createEntityAdapter()` создаёт и возвращает объект с готовыми функциями для нормализованной коллекции.

Функция, которая создаёт такой настроенный объект, называется фабрикой. Здесь фабрика — `createEntityAdapter`, а `tasksAdapter` — выбранное нами имя переменной с результатом её вызова:

```ts
import { createEntityAdapter } from '@reduxjs/toolkit';

type Task = { id: string; title: string; done: boolean };
const tasksAdapter = createEntityAdapter<Task>();

console.log(typeof tasksAdapter.getInitialState); // 'function'
console.log(typeof tasksAdapter.addOne);          // 'function'
console.log(tasksAdapter.getInitialState());     // { ids: [], entities: {} }
```

В возвращённом объекте также есть `updateOne`, `removeOne`, `setAll`, `getSelectors` и другие методы. Это обычные JavaScript-функции из библиотеки. Они не появляются из имени `Task` или из данных сервера.

`<Task>` нужен TypeScript: он проверяет, какие записи можно передавать методам. Этот тип не генерирует код во время выполнения. По умолчанию adapter читает идентификатор из поля `id`. Если поле называется иначе, передай настройку `selectId`, например `selectId: (task: Task) => task.id` для нашего типа; для поля `taskId` понадобится соответствующий тип и `task => task.taskId`.

Упрощённо устройство результата можно представить так:

```text
createEntityAdapter() возвращает объект
  getInitialState → готовая функция создания состояния
  addOne          → готовая функция добавления записи
  updateOne       → готовая функция изменения записи
  removeOne       → готовая функция удаления записи
  getSelectors    → готовая функция создания селекторов
```

## Как готовые методы работают с данными

`getInitialState()` возвращает обычный объект данных. Сам adapter не хранит в себе список задач и не создаёт store.

```ts
const emptyState = tasksAdapter.getInitialState();
const nextState = tasksAdapter.addOne(emptyState, {
  id: '1', title: 'Понять adapter', done: false,
});

console.log(nextState);
// {
//   ids: ['1'],
//   entities: { '1': { id: '1', title: 'Понять adapter', done: false } }
// }
console.log(emptyState); // { ids: [], entities: {} }
```

Это продолжение предыдущего примера: `addOne` получает **состояние коллекции и запись**, затем возвращает следующее состояние. При вызове вне Immer-обработчика используй возвращённый результат, как здесь. Если запись с таким id уже существует, `addOne` её не заменяет.

Внутри обработчика `createSlice` методы могут работать с черновиком Immer. Поэтому их удобно передавать прямо в `reducers`, без собственной функции-обёртки.

## Подключаем готовый обработчик к slice

```ts
import { createEntityAdapter, createSlice } from '@reduxjs/toolkit';
type Task = { id: string; title: string; done: boolean };
export const tasksAdapter = createEntityAdapter<Task>();
export const tasksSlice = createSlice({
  name: 'tasks',
  initialState: tasksAdapter.getInitialState(),
  reducers: {
    added: tasksAdapter.addOne,
    updated: tasksAdapter.updateOne,
    removed: tasksAdapter.removeOne,
  },
});
```

Разберём две строки конфигурации:

- `initialState: tasksAdapter.getInitialState()` **вызывает** готовую функцию и передаёт пустой объект коллекции в slice.
- `added: tasksAdapter.addOne` передаёт **ссылку на готовую функцию** как обработчик действия. Здесь нет `()`: при создании slice добавлять запись ещё не нужно.

`createSlice` создаёт action creator с выбранным нами именем `added`. После подключения reducer к store отправляем действие:

```ts
store.dispatch(tasksSlice.actions.added({
  id: '1', title: 'Понять adapter', done: false,
}));
```

Порядок работы: `added(task)` создаёт action с задачей в `payload` → dispatch передаёт его в store → reducer slice вызывает готовый `addOne` с состоянием слайса и действием → метод обновляет `ids` и `entities`.

**`tasksAdapter.addOne` и `tasksSlice.actions.added` — разные функции.** Первая обрабатывает данные коллекции; вторая только создаёт action. Методы adapter поддерживают передачу как самой записи, так и action с записью в `payload`, поэтому работают в обоих примерах.

Если нужен автоматически поддерживаемый порядок, задай `sortComparer` при создании adapter, например `(a, b) => a.title.localeCompare(b.title)`. Тогда его операции будут поддерживать `ids` в порядке сравнения. Без `sortComparer` adapter не сортирует записи по названию; нужный порядок нужно продумывать явно. При добавлении и удалении используй операции adapter, чтобы `ids` и `entities` оставались согласованными.

`addOne` работает с сущностью; `updateOne` — с `{ id, changes }`; `removeOne` — с id. При прямом вызове первым аргументом передаётся состояние коллекции; в обработчике slice его передаёт Redux Toolkit. Обновление через `updateOne` поверхностное: вложенный объект в `changes` заменяется целиком, а не глубоко сливается.

```ts
store.dispatch(tasksSlice.actions.updated({
  id: '2', changes: { done: true },
}));
```

Здесь `store` подключает этот reducer под ключом `tasks`. Для селекторов передай adapter путь к его состоянию:

```ts
type RootState = ReturnType<typeof store.getState>;
const selectors = tasksAdapter.getSelectors<RootState>(state => state.tasks);
const all = selectors.selectAll(store.getState());
const task = selectors.selectById(store.getState(), '2');
```

## Не путай две задачи

Нормализация помогает хранить сущности и обновлять их по id. Она не решает автоматически загрузку с сервера, дедупликацию запросов или синхронизацию разных кэш-записей RTK Query.

**Эксперимент:** добавь запись в стенде, открой JSON и сравни `ids` с ключами `entities`. Затем переключи задачу и проверь, что id сохранился, а `done` изменился.

## Что запомнить

Adapter предоставляет форму состояния, CRUD-операции и селекторы. Выбирай её, когда операции по id и работа с коллекциями действительно упрощают код.
