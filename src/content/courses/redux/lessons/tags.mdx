# Tags и автоматическое обновление

<div className="learning-note"><strong>После урока ты сможешь</strong><p>Связать mutation с затронутыми query-результатами через tags.</p></div>

Перед началом: пройди [предыдущий урок](/redux/lessons/mutations/).

## Сообщаем, какие данные устарели

Tag — метка результата запроса. Query сообщает, какие метки он предоставляет; mutation — какие делает недействительными. Если затронутая запись имеет активную подписку, RTK Query повторно запрашивает её. Неиспользуемая затронутая запись удаляется из кэша.

```ts
export const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: '/api/' }),
  tagTypes: ['Post'],
  endpoints: builder => ({
    getPost: builder.query<Post, number>({
      query: id => `posts/${id}`,
      providesTags: (_result, _error, id) => [{ type: 'Post', id }],
    }),
    updatePost: builder.mutation<Post, Post>({
      query: ({ id, ...body }) => ({ url: `posts/${id}`, method: 'PATCH', body }),
      invalidatesTags: (_result, error, arg) => error ? [] : [{ type: 'Post', id: arg.id }],
    }),
  }),
});
```

Импорты `createApi`, `fetchBaseQuery` и тип `Post` такие же, как в уроке 12. Здесь при ошибке tags не инвалидируются. Это выбранная политика: статический `invalidatesTags` может инвалидировать данные и после обработанной ошибки.

## Общая метка или конкретная запись

Метка `'Post'` затронет все результаты, предоставляющие этот тип. `{ type: 'Post', id: 1 }` позволяет ограничить обновление. Выбирай детализацию по реальным зависимостям, а не по желанию минимизировать любой сетевой запрос.

Для списка часто используют специальный id `'LIST'`. Запрос списка предоставляет LIST и метки своих элементов. Создание новой записи инвалидирует LIST, потому что новый id ещё не был в предыдущем результате списка.

```ts
providesTags: result => [
  { type: 'Post' as const, id: 'LIST' },
  ...(result ?? []).map(post => ({ type: 'Post' as const, id: post.id })),
]
```

Это фрагмент endpoint `builder.query<Post[], void>`. Представь два списка задач, «Открытые» и «Завершённые». После завершения задачи её id был в открытом списке, а завершённый список ещё не знает о ней. Инвалидация тега задачи обновит открытый список. Чтобы запросить и завершённый, оба списка могут предоставлять общую метку `LIST`, которую инвалидирует mutation.

## Удаление записи при постраничной загрузке

Допустим, сервер отдаёт по две записи. На первой странице id 1 и 2, на второй id 3 и 4. Открыта вторая страница. После удаления записи 1 сервер сдвигает запись 3 на первую страницу, и на второй остаётся только 4. У второй страницы нет тега с id 1, поэтому инвалидация только этого id оставит на экране старый результат.

Добавь эти два endpoints в `endpoints` из первого примера. Здесь `GET /api/posts?page=N` возвращает массив записей, а `DELETE /api/posts/:id` при успехе отвечает статусом 204.

```ts
getPostsPage: builder.query<Post[], number>({
  query: page => `posts?page=${page}`,
  providesTags: posts => [
    { type: 'Post', id: 'PARTIAL-LIST' },
    ...(posts ?? []).map(post => ({ type: 'Post' as const, id: post.id })),
  ],
}),
deletePost: builder.mutation<void, number>({
  query: id => ({ url: `posts/${id}`, method: 'DELETE' }),
  invalidatesTags: (_result, error, id) => error ? [] : [
    { type: 'Post', id },
    { type: 'Post', id: 'PARTIAL-LIST' },
  ],
}),
```

`PARTIAL-LIST` — обычный строковый id тега, который мы сами выбрали. Его предоставляет каждая страница. После удаления RTK Query повторит запросы страниц с активными подписками и уберёт затронутые страницы без подписок из кэша. Тег с id удалённой записи отдельно затронет запрос её карточки.

## Когда RTK Query обработает теги

По умолчанию `invalidationBehavior: 'delayed'`. RTK Query копит инвалидации, пока в этом API выполняются queries или mutations, и обрабатывает их, когда запросы завершатся. Например, две параллельные правки с одним тегом могут привести к одному повторному чтению после обеих. Если запросы постоянно перекрываются и очередь ни разу не пустеет, обновление может откладываться. Поэтому в журнале между PATCH и GET иногда будут другие события.

## Эксперимент

Включи A и B с id 1, дождись загрузки. Измени название через mutation. В журнале появится PATCH, затем GET. Оба компонента получат обновлённую общую запись. При id 2 у B его запись не затрагивается меткой id 1.

Затем включи имитацию ошибки и повтори действие «Mutation + tags». В журнале появятся PATCH и ответ 500. Дополнительного GET от этой mutation не будет, а старое название останется в кэше.

## Что запомнить

Tags описывают зависимости между результатами и изменениями. Это механизм согласования кэша, а не нормализация данных и не прямое редактирование каждой записи.
