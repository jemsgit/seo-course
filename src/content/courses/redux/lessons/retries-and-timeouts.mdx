# Повторные попытки и таймауты

<div className="learning-note"><strong>После урока ты сможешь</strong><p>Отличать повторную попытку от нового запроса пользователя и ограничивать время ожидания ответа.</p></div>

Перед началом: пройди [настройку запросов и ошибок](/redux/lessons/custom-queries/). Временный сбой сервера иногда можно переждать; бесконечное ожидание и повтор любой ошибки — плохие правила по умолчанию.

## Повтор включается явно

Сам `fetchBaseQuery` не добавляет автоматические повторы. Для них есть обёртка `retry`:

```ts
import { createApi, fetchBaseQuery, retry } from '@reduxjs/toolkit/query/react';
const baseQuery = retry(
  fetchBaseQuery({ baseUrl: '/api/', timeout: 5000 }),
  { maxRetries: 2 },
);
export const api = createApi({
  baseQuery,
  endpoints: builder => ({
    getMessage: builder.query<{ message: string }, void>({ query: () => 'message' }),
  }),
});
```

`maxRetries: 2` означает максимум **три вызова**: первая попытка и ещё два повтора. `0` отключает повторы. Если обёртка `retry` используется без настройки этого лимита, её стандартный максимум повторов — 5. Это поведение обёртки, а не любого query RTK Query.

Стандартная задержка между попытками увеличивается и содержит случайный разброс. В лаборатории ниже она намеренно заменена фиксированными 180 мс, чтобы опыт занимал меньше времени.

## Таймаут — ограничение ожидания

`timeout: 5000` у `fetchBaseQuery` задаёт таймаут в миллисекундах. Его можно переопределить в описании отдельного запроса. Когда ожидание превышает лимит, транспорт отменяется, а результат содержит ошибку `TIMEOUT_ERROR`.

Таймаут относится к выполнению отдельной попытки. Повторы и паузы между ними увеличивают общее время ожидания пользователя. Не интерпретируй `timeout` как общий бюджет всех попыток вместе.

## Какие ошибки не стоит повторять

Повтор 401 с теми же учётными данными обычно не решает проблему. Можно прекратить повторы через `retry.fail`:

```ts
const rawBaseQuery = fetchBaseQuery({ baseUrl: '/api/' });
const withRetry = retry(async (args, api, extraOptions) => {
  const result = await rawBaseQuery(args, api, extraOptions);
  if (result.error?.status === 401) {
    retry.fail(result.error, result.meta);
  }
  return result;
}, { maxRetries: 2 });
```

Импортируй `retry` и `fetchBaseQuery` как в первом примере. Для TypeScript тип аргумента можно уточнить через `Parameters<typeof rawBaseQuery>[0]`. Учебный транспорт находится в `src/courses/redux/components/advanced.ts`.

Восстановление сессии после 401 — отдельная задача. `retry.fail` не выполняет refresh токена. Для ошибки валидации также обычно нужна правка ввода, а не повтор того же запроса.

Автоматические повторы mutations требуют осторожности: сервер мог выполнить изменение, даже если клиент не получил ответ. Решение зависит от идемпотентности операции и поддержки сервера. В стенде используется чтение данных.

## Эксперимент

1. Выбери «503, 503, затем успех» и два повтора: получится три попытки и успех.
2. Оставь тот же сценарий, но разреши один повтор: лимит закончится до успеха.
3. Выбери 401: повторов не будет, даже если они разрешены.
4. Выбери медленный ответ: каждая попытка превысит учебный таймаут 120 мс.
