# Сессия в RTK Query

<div className="learning-note"><strong>После урока ты сможешь</strong><p>Скоординировать обновление сессии и проверить, что после выхода приватные данные исчезли из кэша.</p></div>

Перед началом повтори [настройку baseQuery](/redux/lessons/custom-queries/) и [работу кэша](/redux/lessons/cache/).

## Два запроса получили 401

Страница одновременно запрашивает профиль и список задач. Срок действия доступа истёк, поэтому оба запроса получают 401. Если каждый сам вызовет refresh, сервер получит два запроса на обновление одной сессии. При ротации refresh-токена первый вызов может сделать данные для второго уже недействительными.

В лаборатории запросы делят один promise обновления. Первый запрос с 401 создаёт его, второй ждёт тот же promise. После успешного refresh каждый повторяет своё чтение один раз. Если 401 пришёл с запозданием и относится к прежним учётным данным, запрос сразу пробует актуальные.

Ниже фрагмент учебного `baseQuery`. `owner` — объект сессии, который запрос запомнил на старте, а `version` — версия использованных учётных данных.

```ts
if (!result.error || session !== owner || signal.aborted) return result;

if (owner.credentialVersion === version) {
  owner.refresh ??= refresh(owner).finally(() => { delete owner.refresh; });
  await owner.refresh;
}

if (session !== owner || signal.aborted) return result;
return read(panel, owner, owner.credentialVersion);
```

Учебный refresh завершается успешно, пока сессия активна. В приложении различай истёкший доступ, отказ в обновлении сессии и временный сетевой сбой. Если сервер подтвердил, что сессия больше недействительна, заверши её и верни пользователя к входу. Если повторный запрос снова получил 401, передай ошибку вызывающему коду. Схема обновления, включая то, какие операции можно повторять, зависит от API. В опыте повторяются только чтения.

## Что происходит при выходе

Ключ запроса определяется endpoint и аргументом. Кнопки «Войти как Анна» и «Войти как Борис» запускают одинаковые `privatePanel('profile')` и `privatePanel('tasks')`. Заголовок авторизации сам по себе ключ не меняет. Если оставить старый кэш, запрос под новым аккаунтом может получить данные прежнего пользователя.

При выходе стенд помечает сессию завершённой, отменяет выполняющиеся запросы к приватному API и вызывает `store.dispatch(api.util.resetApiState())`. Компонент передаёт `skipToken`, чтобы снять подписки и прекратить приватные чтения. `resetApiState()` сбрасывает весь экземпляр API, поэтому здесь используется отдельный учебный API для приватных данных.

```ts
session = undefined;
for (const request of store.dispatch(api.util.getRunningQueriesThunk())) {
  request.abort();
}
store.dispatch(api.util.resetApiState());
```

Асинхронный refresh может закончиться уже после выхода или после входа под другой учётной записью. Перед записью новых учётных данных стенд проверяет, что объект сессии всё ещё тот же. Запросы, которые ждали refresh, проверяют это ещё раз перед повторным чтением.

## Лаборатория

1. Войди как Анна. В журнале появятся два исходных GET, два ответа 401, один POST на refresh и по одному повторному GET для профиля и задач. Первый 401 может запустить refresh ещё до того, как придёт второй.
2. Выйди после загрузки. Профиль и задачи сразу исчезнут. Войди снова и нажми «Выйти», пока в журнале уже есть POST на refresh, а профиль ещё загружается. Поздний ответ будет отброшен.
3. После выхода войди как Борис. Убедись, что на экране появляются данные Бориса, хотя аргументы запросов остались прежними.

Стенд имитирует HTTP в памяти. При каждом входе он специально начинает с истёкшего доступа.
