# Кэш и общие подписки

<div className="learning-note"><strong>После урока ты сможешь</strong><p>Предсказывать, когда появится запрос и когда удалится запись кэша.</p></div>

Перед началом: пройди [предыдущий урок](/redux/lessons/queries/).

## Два компонента — один результат

Кэш RTK Query организован по endpoint и сериализованному аргументу. Если два компонента подписались на `getPost(1)`, они разделяют запись и её обновления. При обычном поведении второй компонент получает готовые данные, а не создаёт независимую копию.

Стандартная сериализация аргументов учитывает значения объекта; новый объект с теми же сериализуемыми полями сам по себе не означает новый запрос. Конфигурация endpoint может изменить сериализацию, но сначала освой стандартные правила.

## Время жизни после последнего потребителя

```ts
getPost: builder.query<Post, number>({
  query: id => `posts/${id}`,
  keepUnusedDataFor: 30,
})
```

Это настройка endpoint из API урока 12. Время задаётся в секундах. По умолчанию неиспользуемые данные хранятся 60 секунд. Отсчёт начинается после исчезновения **последней** подписки на запись, а не после каждого ответа сервера.

Если новый потребитель появился до удаления записи, он может получить данные из кэша. `keepUnusedDataFor` не является обещанием свежести и сам не запускает обновление. Для обновления есть tags, refetch и другие политики.

### Хранение и повторный запрос на одном примере

Оставим `keepUnusedDataFor: 30` в endpoint и добавим настройку к вызову хука:

```tsx
const post = api.useGetPostQuery(1, { refetchOnMountOrArgChange: 10 });
```

Запрос успешно завершился на нулевой секунде. Последний подписчик ушёл на пятой, а новый появился на пятнадцатой. Кэш ещё доступен, потому что без подписчиков прошло только 10 из 30 секунд. Но с последнего успешного ответа прошло 15 секунд, поэтому новый подписчик сразу увидит сохранённые данные, а RTK Query параллельно запустит GET.

Значение `10` проверяется при новой подписке, в том числе при смене аргумента. Это порог возраста результата в секундах. Пока компонент просто остаётся открытым, периодический запрос эта настройка не запускает. Если на момент подписки записи уже нет в кэше, RTK Query загрузит её независимо от порога.

## Кэш результата не равен общей базе сущностей

Если одна запись пришла через `getPost(1)`, а другая — внутри `getPosts()`, RTK Query не объединяет их автоматически в единственную нормализованную сущность. Это разные результаты запросов. Tags помогают сделать их согласованными через повторную загрузку.

Изменение данных на сервере вне приложения само по себе не уведомляет браузер. Нужен refetch, polling, события соединения или streaming — в зависимости от задачи.

## Эксперимент по шагам

1. После сброса дождись A: выполнен один запрос.
2. Включи B с id 1: при готовом кэше дополнительный запрос не требуется.
3. Отключи A: B продолжает удерживать запись.
4. Отключи B и подожди больше трёх секунд: запись исчезнет.
5. Включи A снова: понадобится новый запрос.

В стенде время хранения сокращено до трёх секунд. Это учебная настройка, а не стандартное значение библиотеки.

## Что запомнить

Подписки определяют, нужен ли результат потребителям. Время хранения неиспользуемой записи и политика её актуальности — разные настройки.
