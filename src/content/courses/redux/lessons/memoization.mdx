# Мемоизация и перерисовки

<div className="learning-note"><strong>После урока ты сможешь</strong><p>Понимать, когда селектор пересчитывает результат и зачем сохранять ссылку.</p></div>

Перед началом: пройди [предыдущий урок](/redux/lessons/selectors/).

## Одинаковые данные, новый массив

Пусть компонент читает `tasks.filter(...)`. При каждом вызове селектора получается новый массив даже тогда, когда задачи не изменились. React Redux по умолчанию сравнивает ссылки через `===`, а не содержимое массивов.

`createSelector` разделяет чтение входов и преобразование. Если выбранные входные значения не изменились, сохранённый результат можно использовать повторно.

```ts
import { createSelector } from '@reduxjs/toolkit';
type Task = { id: string; done: boolean };
type State = { tasks: Task[]; filter: 'all' | 'active'; theme: string };
const selectTasks = (state: State) => state.tasks;
const selectFilter = (state: State) => state.filter;
export const selectVisible = createSelector(
  [selectTasks, selectFilter],
  (tasks, filter) => filter === 'all' ? tasks : tasks.filter(task => !task.done),
);
```

Изменение `theme` не меняет входы этого преобразования. Не нужно заново фильтровать задачи. Но изменение массива `tasks` или фильтра требует нового результата.

## Можно ли передавать стрелочную функцию прямо в useSelector?

**Да. Для простого чтения поля это обычный и допустимый вариант:**

```tsx
function TaskList() {
  const tasks = useAppSelector(state => state.tasks);
  // Отображение tasks…
}
```

Здесь и далее используем типизированный `useAppSelector` из [урока 4](/redux/lessons/react-redux/). Его параметр `state` — всё корневое состояние store; селектор выбирает из него нужные данные. Это отличается от параметра `state` обработчика slice, который получает только состояние своего слайса.

При каждом вызове компонента создаётся новая функция-стрелка. Это само по себе не ошибка и не причина бесконечных рендеров. Чтение `state.tasks` дешёвое, а ссылка на массив остаётся прежней, пока соответствующие данные не изменились.

Можно вынести тот же селектор на уровень модуля:

```tsx
// Вне компонента: одна функция для всех его рендеров.
const selectTasks = (state: State) => state.tasks;

function TaskList() {
  const tasks = useAppSelector(selectTasks);
  // Отображение tasks…
}
```

Для примеров используем тип `State` из начала урока. В приложении вместо него обычно импортируют `RootState` из store.

Вынесенная функция удобна для повторного использования, именования логики и тестирования. Стабильная ссылка также позволяет `useSelector` при неизменившемся состоянии повторно использовать результат на рендере, не вызывая селектор заново. Для простого чтения поля эта экономия обычно мала; выносить каждую стрелку ради неё не требуется.

Объявление `const selectTasks = ...` **внутри** компонента всё равно создаёт функцию при каждом рендере. Важна область создания, а не выбор между стрелкой и `function`.

## Не путай ссылку на функцию и ссылку на результат

Это две разные вещи:

| Что сравниваем | На что влияет |
| --- | --- |
| Ссылку на функцию-селектор | Можно ли переиспользовать работу hook на рендере при тех же входах |
| Результат селектора | Нужно ли обновлять компонент из-за изменения выбранных данных store |

По умолчанию `useSelector` сравнивает результаты через `===`. Само вынесение функции не делает результат стабильным:

```ts
// Функция постоянная, но каждый её вызов создаёт новый массив.
const selectActiveTasks = (state: State) =>
  state.tasks.filter(task => !task.done);
```

Если передать её в `useAppSelector`, новая ссылка результата может привести к лишнему обновлению после несвязанного изменения store. Здесь нужен мемоизированный результат, например через `createSelector`. Аналогичная проблема бывает с `state => ({ tasks: state.tasks })`: это новый объект при каждом вызове. Для нескольких полей можно использовать отдельные вызовы hook, мемоизированный селектор или подходящий `equalityFn`, например `shallowEqual`.

## Где создавать createSelector

Обычный селектор не хранит своего кэша. У селектора, созданного через `createSelector`, есть кэш, поэтому его экземпляр нужно сохранять между рендерами:

```tsx
// Вне компонента: экземпляр и его кэш сохраняются.
const selectActiveTasks = createSelector(
  [(state: State) => state.tasks],
  tasks => tasks.filter(task => !task.done),
);

function TaskList() {
  const tasks = useAppSelector(selectActiveTasks);
  // Отображение tasks…
}
```

Если вызвать `createSelector(...)` непосредственно в теле `TaskList` на каждом рендере, каждый раз появится новый экземпляр с новым кэшем. Именно это лишает мемоизацию накопленного результата. Сам по себе inline callback в `useSelector` такой проблемы не создаёт, если он вызывает уже существующий мемоизированный селектор.

Входные селекторы обычно читают поля. Не пиши `state => state.tasks.filter(...)` во входе `createSelector`: это уже преобразование с новой ссылкой. Перенеси `filter()` в последнюю функцию, как в примере выше.

## Если селектору нужен prop компонента

Для простого поиска по id удобно замкнуть prop в стрелочной функции:

```tsx
function TaskRow({ id }: { id: string }) {
  const task = useAppSelector(state => state.tasks.find(task => task.id === id));
  return <span>{task ? task.id : 'Задача не найдена'}</span>;
}
```

`find` возвращает существующий объект или `undefined`, а не создаёт новый объект задачи. Не нужно автоматически добавлять `useCallback` к каждому такому чтению.

`useCallback` стабилизирует **функцию**, но не запоминает результат `filter` или другого вычисления. Для этого используется мемоизация селектора. Если дорогому селектору нужен отдельный кэш на экземпляр компонента, можно создать его через фабрику и сохранить с `useMemo`. Это отдельный приём, а не обязательное правило для любого селектора с props.

### Практическое правило

- Простое чтение поля или поиск по id можно писать inline.
- Общую логику удобно выносить в именованные селекторы на уровень модуля.
- Для вычисления нового массива или объекта оцени необходимость `createSelector`.
- Экземпляр `createSelector` сохраняй между рендерами; одна только стабильная ссылка на обычную функцию не мемоизирует её результат.

## Не обещаем «ровно один рендер»

На рендер React влияют также props, родитель, context и режим разработки. Мемоизация селектора убирает лишние вычисления и помогает сохранить ссылку; она не гарантирует полное отсутствие рендеров по другим причинам.

Для наблюдения вычислений можно вызвать `selectVisible.recomputations()`. Сравни результат после двух вызовов с одинаковым state и после передачи нового массива задач. Этот счётчик относится к результирующей функции, а не к DOM.

**Задание:** добавь в состояние поле `theme`. Предскажи, должен ли селектор списка пересчитать результат при изменении только этого поля. Ответ: нет, его входы остались прежними. Такой сценарий проверяется в тестах учебника.

## Что запомнить

Стабильные входы позволяют сохранить результат преобразования. Мемоизируй вычисления, а не простой доступ к полю, и измеряй эффект в нужном месте.
