# Redux в реальном приложении: правила и типичные ошибки

<div className="learning-note"><strong>После урока ты сможешь</strong><p>Проверить небольшую Redux-функциональность на типичные ошибки и объяснить свои архитектурные решения.</p></div>

Перед началом: пригодятся [slices и события](/redux/lessons/payload-and-events/), [селекторы](/redux/lessons/selectors/) и [организация API](/redux/lessons/api-organization/). Это заключительный разбор решений; собирать отдельный проект не требуется.

## Обязательное правило или удобная договорённость?

Официальный Style Guide различает критичные правила корректности и рекомендации по организации кода. Чистота reducers и иммутабельность защищают поведение программы. Структура папок помогает сопровождению, но допускает разные решения. Ниже разбираем последствия, чтобы выбирать осознанно.

## 1. Храни исходные данные, вычисляй представление

**Найди проблему:** при добавлении задачи какой ещё счётчик придётся обновить?

```ts
const state = {
  tasks: [{ id: '1', done: false }],
  activeCount: 1,
};
```

Если `activeCount` полностью определяется текущими задачами, вторая копия факта может устареть. Список изменили, а счётчик забыли. Вычисляй его селектором.

<details>
<summary>Показать исправление и разбор</summary>

```ts
type State = { tasks: { id: string; done: boolean }[] };
const selectActiveCount = (state: State) =>
  state.tasks.filter(task => !task.done).length;
```

Здесь список небольшой. Для дорогого вычисления или результата-массива пригодится `createSelector`. Если сервер возвращает общее число записей, а клиент загрузил только одну страницу, это уже отдельные исходные данные: локальным подсчётом их не заменить.

</details>

## 2. Храни выбранный id, если нужна актуальная сущность

**Найди проблему:** что будет с `selectedTask`, когда сервер обновит задачу в списке?

```ts
const state = {
  tasks: [{ id: '1', title: 'Первое название' }],
  selectedTask: { id: '1', title: 'Первое название' },
};
```

<details>
<summary>Показать исправление и разбор</summary>

```ts
type Task = { id: string; title: string };
type State = { tasks: Task[]; selectedTaskId: string | null };
const selectSelectedTask = (state: State) =>
  state.tasks.find(task => task.id === state.selectedTaskId);
```

При удалении записи селектор вернёт `undefined`; интерфейс должен обработать этот случай. Для нормализованных данных читай `entities[id]`.

Редактируемый черновик формы может быть отдельной копией, поскольку у него своя роль. Важно явно определить, когда он создаётся, сохраняется и сбрасывается.

</details>

## 3. Описывай действие как событие

Сравни два способа описать завершение сессии:

```ts
// Компонент управляет внутренними деталями нескольких slices.
dispatch(clearTasks());
dispatch(resetFilter());
dispatch(clearSelection());

// Компонент сообщает о событии приложения.
dispatch(sessionEnded());
```

Во втором варианте каждый затронутый slice реагирует на `sessionEnded` через `extraReducers`. Название помогает понять событие в DevTools, а правила реакции остаются рядом с состоянием. Несколько последовательных dispatch также могут дать наблюдателям промежуточные состояния.

Это не запрет всех действий вида `setX`. Простое изменение фильтра вполне может иметь такой смысл. Ищи предметное событие, когда несколько обновлений представляют одну логическую операцию.

## 4. Делай невозможные состояния труднее выразимыми

**Найди проблему:** сколько противоречивых сочетаний допускают три независимых флага?

```ts
const request = { isLoading: true, isSuccess: true, isError: true };
```

Для жизненного цикла одной самодельной операции проще использовать статус:

```ts
type Status = 'idle' | 'pending' | 'succeeded' | 'failed';
type RequestState = { status: Status; error: string | null };
```

В обработчике начала выставляй `pending` и очищай ошибку. При успехе — `succeeded`, при неуспехе — `failed` с описанием ошибки. Для строгой связи статуса и доступных данных можно развить это в discriminated union TypeScript.

Статус не запрещает неправильные переходы автоматически. Если повторный запуск во время выполнения недопустим, добавь условие. Если параллельные операции разрешены, отслеживай их отдельно, например по id или requestId.

**В RTK Query не заменяй готовые флаги своим единственным status.** Они отражают разные свойства: старые данные могут оставаться доступны во время новой загрузки. Проблема выше относится к самодельным флагам с взаимоисключающим смыслом.

## 5. Держи данные сериализуемыми, reducers — чистыми

**Найди проблему:** какие строки мешают воспроизвести результат reducer по тем же входам?

```ts
// Пример ошибочного обработчика createSlice:
added(state, action) {
  state.items.push({ id: crypto.randomUUID(), title: action.payload });
  localStorage.setItem('tasks', JSON.stringify(state.items));
}
```

Случайный id и запись во внешнее хранилище не относятся к вычислению следующего состояния. Создай id до dispatch или в `prepare`, а запись вынеси в подходящий эффект или listener.

```ts
// В обработчике пользовательского события:
dispatch(added({ id: crypto.randomUUID(), title }));

// В reducers createSlice:
added(state, action) {
  state.items.push(action.payload);
}
```

Это фрагменты для slice с массивом `items`. В TypeScript укажи `PayloadAction<{ id: string; title: string }>` для action. Immer поддерживает изменение черновика внутри обработчика, но не разрешает изменять данные, полученные из `store.getState()`, снаружи.

Не сохраняй функции, Promise и DOM-элементы в обычных actions и state. Дату часто удобно хранить строкой или timestamp. Не отключай стандартные проверки Toolkit целиком ради одного предупреждения: сначала выясни, какие данные пересекли границу Redux. Для интеграции с особыми middleware допустимы точечные исключения при понимании их контракта.

## 6. Выбирай инструмент по задаче

| Задача | С чего начать |
| --- | --- |
| Локальный черновик, открытая панель | Состояние React, если другим потребителям оно не нужно |
| Загрузка и кэш серверных данных | RTK Query |
| Реакция на action, debounce, отложенный workflow | Listener middleware |
| Логика с getState и несколькими dispatch | Thunk; createAsyncThunk для подходящей асинхронной операции |
| Чистое вычисление из state | Селектор |

Не копируй query-результат в обычный slice без отдельной причины. Для выбранной записи достаточно id; для локальных изменений до сохранения может понадобиться самостоятельный черновик.

## 7. Организуй код по функциональности

Структура может выглядеть так:

```text
src/
  app/
    store.ts
    hooks.ts
  services/
    baseApi.ts
  features/
    tasks/
      tasksSlice.ts
      tasksApi.ts
      selectors.ts
      TaskList.tsx
```

В `tasksSlice.ts` находятся клиентские настройки задач, а `tasksApi.ts` расширяет общий API через `injectEndpoints`. Не нужно хранить серверный список в обоих местах. Для маленькой функции отдельные файлы селекторов или API могут быть избыточны — сохраняй понятные границы, а не максимальное число папок.

Обычно связанные endpoints одного базового URL принадлежат одному API slice. Разделяй их по файлам через `injectEndpoints`: tags работают внутри одного API slice, а каждый новый `createApi` добавляет собственное middleware. Разные независимые API могут обоснованно иметь разные slices.

## Самопроверка: проверяем решение целиком

```ts
// Схематичный фрагмент приложения:
const selectedTask = tasks.find(task => task.id === selectedTaskId);
const [draftTitle, setDraftTitle] = useState(selectedTask?.title ?? '');
```

Если пользователь выберет другую задачу, начальный аргумент `useState` сам по себе не пересоздаст черновик. Продумай явный сброс, компонент с `key` выбранной записи или другое правило переключения. Копия оправдана, но ей всё равно нужен жизненный цикл.

## Что проверить перед завершением работы

- У каждого значения понятен владелец; вычисляемые данные не дублируются без причины.
- События объясняют происходящее, reducers не выполняют побочные эффекты.
- Ошибка и повторная загрузка имеют понятное поведение в UI.
- Подписки и внешние ресурсы освобождаются при завершении использования.
- Тесты проверяют результат для пользователя, а оптимизации опираются на наблюдение.

Для повторения основ открой [архитектуру и тестирование](/redux/lessons/final-project/) или вернись к нужной теме в программе. Эта глава — ориентир для проверки решений, а не требование применять все инструменты к каждому экрану.
