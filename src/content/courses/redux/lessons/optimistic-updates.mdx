# Оптимистические обновления

## Интерфейс не обязан ждать сеть

При оптимистическом обновлении UI сразу показывает предполагаемый успех. Если сервер отклонит изменение, приложение отменяет локальную правку. Такой подход полезен для небольших обратимых действий; для сложных операций ожидание подтверждения может быть понятнее.

```ts
updatePost: builder.mutation<Post, Post>({
  query: ({ id, ...body }) => ({ url: `posts/${id}`, method: 'PATCH', body }),
  async onQueryStarted(arg, { dispatch, queryFulfilled }) {
    const patch = dispatch(api.util.updateQueryData('getPost', arg.id, draft => {
      draft.title = arg.title;
    }));
    try {
      const { data: saved } = await queryFulfilled;
      dispatch(api.util.updateQueryData('getPost', arg.id, () => saved));
    } catch {
      patch.undo();
    }
  },
})
```

Это фрагмент API из урока 12, где уже объявлен `getPost`. Он рассчитан на одну правку записи за раз и предполагает, что PATCH возвращает полную запись. `onQueryStarted` запускается в начале операции. Первый патч показывает введённое название, а после `queryFulfilled` второй патч заменяет карточку ответом сервера. Например, сервер может убрать лишние пробелы. При ошибке `patch.undo()` восстанавливает значение до первого патча. `updateQueryData` работает с существующей записью кэша по точной паре endpoint и аргумента.

## Пессимистический вариант

Если сначала нужно подтверждение сервера, дождись `queryFulfilled`, затем используй возвращённые данные:

```ts
const { data: saved } = await queryFulfilled;
dispatch(api.util.updateQueryData('getPost', arg.id, draft => {
  draft.title = saved.title;
}));
```

Этот фрагмент находится внутри `onQueryStarted` и должен иметь обработку ошибки. Он полезен, когда сервер преобразует отправленный текст или добавляет поля. Для простого поддержания актуальности часто достаточно tags без ручных патчей.

## Что может пойти не так

Патч `getPost(1)` не меняет автоматически список `getPosts()`. Если UI читает обе записи, обнови нужные результаты или инвалидируй связанные tags.

Представь, что первая правка изменила заголовок с «Исходный» на «Первый», а вторая сразу поставила «Второй». Если первая правка завершится ошибкой, её `undo()` восстановит «Исходный» поверх «Второго». Прямое применение ответа на ранний запрос тоже может затереть более свежий локальный патч.

Лаборатория оставляет оптимистический патч в `onQueryStarted`, а для сверки использует тег карточки:

```ts
invalidatesTags: (_result, _error, { id }) => [{ type: 'Post', id }],
```

В этой лаборатории тег инвалидируется и после успеха, и после обработанной ошибки API. При стандартной отложенной инвалидации RTK Query дожидается завершения обеих правок, затем повторно запрашивает карточку с активной подпиской. Пока идёт сверка, на экране может оставаться оптимистичное название. Итог берётся из ответа на GET. Если приложению нужно гарантировать, что более поздняя правка победит на сервере, порядок записи нужно согласовать с сервером или отправлять правки последовательно.

## Эксперимент

1. Введи «Новое   название» с несколькими пробелами и нажми «Оптимистически». В кэше сначала появится введённая строка. После PATCH и GET останется «Новое название» с одним пробелом. Разницу удобно смотреть в JSON кэша, потому что в заголовке браузер схлопывает пробелы.
2. Включи ошибку и повтори с другим названием. После ответа 500 в журнале появится GET, и карточка снова покажет сохранённое название.
3. Нажми «Запустить две правки». Стенд отправит две правки одной записи подряд. Первая получит 500, вторая сохранится. После обеих операций и повторного GET карточка покажет «Вторая правка». Проверь порядок событий в журнале учебного API.

## Что запомнить

Оптимистический UI — предположение с планом восстановления. Самый важный код здесь — не только правка, но и обработка неуспеха.
